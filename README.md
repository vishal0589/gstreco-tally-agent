# gstreco-tally-agent

Windows agent that polls Tally Prime (3.x+) on the customer's LAN and pushes vouchers / masters to GST Reco over HTTPS. Written in Go, distributed as a single ~10 MB binary, installed as a Windows service with a systray companion.

See `~/GST_Reco/docs/plans/2026-04-tally-agent/master-plan.md` for the full architecture + decisions log (server-side repo, master plan).

## Installer-first preview

The primary Windows onboarding flow is now **installer-first**:

- `gstreco-tally-installer.exe` is the happy path for normal Windows users.
- The installer starts a browser-authorized session with GST Reco, opens the approval page, claims credentials after approval, installs or repairs the Windows service, and runs discovery-first against the common Tally ports.
- `agentctl pair --code` and app-side `install.ps1` remain available as **support fallbacks**, not the default product path.
- Manual Tally port entry is a fallback-only step after automatic discovery fails.

## Status

Phase A + Phase B + v0.1.2 shipped. Pilot install on PLLUM uncovered four pre-existing install-path bugs (TLS 1.2 not forced; `2>$null` not suppressing native errors under `ErrorActionPreference=Stop`; `$env:ProgramFiles` resolving to `(x86)` under 32-bit PowerShell; Windows Credential Manager scoped per-user so `LocalSystem`-running service couldn't read what `Administrator`-running pair wrote). v0.1.2 fixes all four:

- New `internal/secretstore` package replaces the per-user OS keyring with a file-based AES-GCM store at `%ProgramData%\GST Reco\agent\secrets\`, key derived via HKDF-SHA256 from the machine ID. Cross-user accessible by design, so the service-as-LocalSystem reads what pair-as-Administrator wrote. ACL'd to SYSTEM + Administrators on first write via `icacls`.
- `internal/autodiscover` now honours `cfg.TallyEndpoints` first (set by `agentctl discover --ports` or by the install-time `GSTRECO_TALLY_PORTS` env var), falls back to the default port range only when the config is empty.
- Default discovery range widened from 9000–9009 to 9000–9020 plus alternates `2026, 8989` to cover the common non-default ports we've seen in pilot installs.
- `install.ps1` (in the GST_Reco repo) prepends TLS 1.2, uses `Get-Service` existence check before stop/uninstall, hardcodes the install dir to `C:\Program Files\GST Reco Agent`, and accepts `GSTRECO_TALLY_PORTS` for non-default-port customers.

A fresh customer install is now: download the Windows installer, approve the machine in the browser, let the installer try the common Tally ports automatically, and only enter custom ports if discovery still fails. The older PowerShell flow remains available for recovery and support.

**v0.1.3 — Tally Prime 6.x discovery hardening.** The PLLUM pilot install on Tally Prime 6.1 surfaced three protocol assumptions baked into v0.1.2's discovery path that only held for Tally Prime 3.x:

- **Company-list `<TYPE>Data</TYPE>` rejected.** Tally Prime 6.x is strict — built-in reports like "List of Companies" must be requested with `<TYPE>Collection</TYPE>` (cross-checked against the Manual2AI Python adapter, which has shipped against the same Tally Prime 6.1 install since 2026-04-19).
- **`$$Version` Function probe doesn't answer reliably.** Tally Prime 6.x returns `STATUS=0 + DESC not found` for the `<TYPE>Function</TYPE><ID>$$Version</ID>` shape. v0.1.3 trusts the company-list response as the authoritative "is this Tally" signal and treats the version probe as best-effort telemetry.
- **V3-only filter dropped Tally Prime 4.x+.** The HTTP/XML protocol for the queries this agent issues is identical across Tally Prime 3.x/4.x/5.x/6.x. v0.1.3 keeps every probe result that responds with a parseable Tally envelope.

Voucher fetch + ingest hardening (UTF-16LE response decoding, inline-TDL voucher collections, strict-OK ingest predicate, voucher-type-name configurability) is queued for v0.1.4. v0.1.3 unblocks discovery; v0.1.4 will harden the actual sync path.

**v0.1.12 — scheduler default moves to working hours + retry-with-backoff.** DIPL Delhi pilot (2026-04-29) demonstrated the brittleness of the pre-v0.1.12 default `"0 2 * * *"` (daily 2am): the scheduler ran at 2am IST when the customer's Tally was closed, every per-kind fetch returned `connectex: No connection could be made because the target machine actively refused it`, the scheduler logged "tick complete" with 0 rows and 4 fatal_errors, and then **waited a full 24 hours** before its next attempt. DIPL appeared "stuck" for 36+ hours despite the agent's heartbeat being healthy.

- **`DefaultSpec` changes from `"0 2 * * *"` → `"0 11,13,15,17 * * *"`** (`internal/scheduler/scheduler.go:22`). 4 ticks per day during the customer's working hours (11am, 1pm, 3pm, 5pm in agent-local timezone — typically IST). Tally is reliably open during those windows. New customers pairing on v0.1.12+ get this default; existing customers keep their config-yaml-set schedule (server-driven schedule sync via heartbeat is a B3 follow-up).
- **`DefaultRetryDelays = [1h, 2h]`** (new) — cron-driven ticks that return a non-nil error from `TickFunc` are retried at +1h, then +2h, before the scheduler waits for the next cron tick. This matches the customer ask "retry in 1/2 hours" and prevents a single transient Tally outage at 11am from waiting until 1pm before recovery.
- `RunNow` (operator-triggered "Sync now" via heartbeat action queue) does **NOT** retry — the operator is already at the dashboard and can re-click. Retries apply only to the scheduled cron path.
- `Stop()` cancels pending retry timers + sets a `stopped` atomic so any race-fired retry goroutine short-circuits before calling `tickFn`. Race-detector clean.
- Retry attempt count + delay logged at `info` per attempt: `scheduler tick failed; queued retry attempt=1 max_attempts=2 delay=1h0m0s`.
- 6 new tests in `internal/scheduler/scheduler_test.go`: working-hours `DefaultSpec` pinned, `DefaultRetryDelays` pinned at [1h, 2h], retry fires after delay on cron-driven failure, retry advances through all delays on repeated failure, empty `RetryDelays` disables retries, retry cancelled by `Stop()`, `RunNow` does NOT retry.

For DIPL specifically: this v0.1.12 default doesn't auto-apply because their `config.yaml` was written with the old `"0 2 * * *"` at pair-time. Operational fix is to edit `C:\ProgramData\GST Reco\agent\config.yaml` and set `schedule_cron: "0 11,13,15,17 * * *"`, then `Restart-Service gstreco-tally-agent`. Server-driven schedule sync via heartbeat ([B3 follow-up](https://github.com/vishal0589/GST_Reco/blob/main/docs/plans/2026-04-tally-agent/master-plan.md)) will close this gap so a future DB-side update propagates to all customers without RDP.

**v0.1.11 — HSN carried through to ingest payload.** Server v0.1.21's migration 00049 added `purchase_invoices.hsn`, and v0.1.23's migration 00050 wired the `upsert_tally_purchase_invoices` RPC to accept the new field — but until v0.1.11 the agent never sent it. The HSN was already extracted into `RawVoucher.InventoryEntries[].HSN` (since v0.1.0), it just stayed agent-side. v0.1.11 carries it through:

- **`IngestVoucherRow.HSN *string`** added in `internal/tally/ingest_types.go` (mirrors the new TS field on the server). `omitempty` so the wire payload stays compact when HSN is absent.
- **`Normalize()`** sets `row.HSN` from the first non-empty inventory entry's `GSTHSNNAME`. `firstInventoryHSN` skips whitespace-only entries (Tally serialises legacy stock-items with `" "` when the HSN master field is blank). Service-only purchases (no `<INVENTORYENTRIES.LIST>`) leave HSN nil — the server-side classifier defaults to `is_capital_good=false` for unknown HSN, which is correct since services are never capital goods.
- **Consolidated vouchers** carry the same first-HSN across every split row. HSN is a voucher-level fact in Tally — inventory entries aren't separately tagged to bill allocations.

This unblocks the v0.1.11 capital-goods classifier (chapters 84/85/90) on real ingested data; before this PR the classifier saw `undefined` for every Tally-sourced row and always marked `is_capital_good=false`.

**v0.1.10 — secretstore: applyDirACL fatal-on-fail + write-verify roundtrip.** DIPL Delhi pilot (2026-04-27) hit the silent-failure variant of `applyDirACL`: the directory-level icacls call failed (probably AV / GPO interference), Set() warned-and-continued, and the file ended up in a directory whose DACL the LocalSystem service couldn't traverse. The agent then 401-looped on every heartbeat with `read hmac secret from keyring failed: Access is denied`, taking 5+ hours to diagnose. v0.1.10 fixes this end-to-end:

- **Fatal**: `applyDirACL` failure now returns from `Set()` instead of warning to stderr. Pair surfaces the error immediately.
- **Write-verify roundtrip**: after `Set()` writes + renames the encrypted file, it does a `getLocked()` round-trip read-back to confirm the resulting file is actually readable + decryptable. Catches EFS / AV / restrictive-DACL cases that cipher succeeds but read fails.
- **Test seam**: `applyDirACLFn` is now a package-level variable so tests can simulate icacls failure deterministically (cross-platform).

Plus `install.ps1` (in GST_Reco repo, separate PR) appends a belt-and-suspenders `icacls /reset /T /grant:r Everyone:(OI)(CI)F /T` on the secrets dir so any prior broken DACL is corrected at install time.

**v0.1.10 — Tally Prime 6.x master-field rename catch-up.** DIPL Delhi pilot (2026-04-27) surfaced 0 % coverage on `trade_name`, `state_code`, `email` despite real GSTINs flowing — the smoking gun that Tally Prime 6.x renamed master-ledger XML elements (the v3 `EMAIL` is now `LEDGEREMAIL`; `STATENAME` is now `LEDSTATENAME`; `LEDGERMOBILE` is now `LEDGERMOBILENO` on some patches). The FETCH list in `internal/tally/master_envelope.go` and the `xmlLedger` struct in `internal/tally/master_parser.go` now ask for + accept all known variants and pick the populated one via the existing `firstNonEmpty` helper. After re-syncing masters on v0.1.10, vendor / customer master coverage on Prime 6.x ledgers jumps from <5 % to ~95 % — vendor portal lists show real names and emails instead of raw GSTINs.

**v0.1.44 (unreleased) — party GSTIN from the ledger master.** Journal and payment vouchers rarely carry a voucher-level `PARTYGSTIN`; Tally keeps the GSTIN on the party's ledger master, which is where its own registers read it. A 2026-10 audit against two clients' Tally GST-input registers found 3,727 journals (₹13.1L of input tax) synced with no GSTIN, so they could never match GSTR-2B. Each sync now reads every ledger's GSTIN once per company (`internal/tally/ledger_gstin.go`: `PARTYGSTIN`, `GSTIN`, `PARTYGSTNUMBER` and the dated `LEDGSTREGDETAILS.LIST` registrations; any group, since accountants keep parties under sub-groups, advances and expense groups) and fills the party GSTIN when the voucher is silent. A party the voucher names (party ledger, or the ledger with bill refs) takes its own ledger's GSTIN and is never swapped for another line; only an inferred party is replaced, and only when exactly one party-capable line carries a GSTIN (never a guess between two). Bank, cash, duties-and-taxes and branch ledgers are recognised by Tally's group tree, not their names. Dated registrations (`LEDGSTREGDETAILS.LIST`) apply as of the voucher date, including "unregistered from" entries. A Tally error reply (`STATUS 0`, `LINEERROR`) is a failed lookup, never an empty map. Invoice-family vouchers without `PARTYGSTIN` get the same fill. The map is cached for ten minutes per company so all lanes of a tick share one Tally request; a failed lookup is a warning and the voucher is sent as before.

**v0.1.44 (unreleased) — read each company from the Tally port it is open on.** On a shared server Tally instances start and stop through the day, two companies share one install, and a company opened in a second copy of an install lands on whichever copy holds the port. The agent read only the mapped port, so a company open elsewhere was never synced (AAM and HaH went unsynced from August), and one open nowhere produced a failed request per voucher kind with no plain reason. Before each tick the agent now probes the mapped ports plus every port a `tally.exe` is listening on (read from the Windows socket table, `internal/tally/listeners_windows.go`), then reads each company where it is open (`syncrun.ResolveMappingEndpoints`): its mapped port when the company is there, else the one other port that has it open (read there via `FetchEndpoint`, while ingest keeps reporting the mapped endpoint the server uses to find the mapping's GSTIN); never a guess between two copies, never a same-named company with a different Tally GUID, and local aliases (localhost, the host name) count as one Tally; and one clear line ("… is not open in any Tally on this machine; the Tally at :9012 did not answer") when it is open nowhere. Probes time out after 8 s, so a hung Tally is skipped for the tick instead of holding every voucher kind for minutes and starving the companies after it.

**v0.1.45 (unreleased) — the agent updates itself.** Until now an agent only logged that a newer release existed, so every fix needed someone at the client's server to rerun the installer. Every 6 hours the daemon checks `/api/tally/agent/version`; when `latest` is a higher release than its own and the server allows it (`auto_update.enabled`, the GST Reco kill switch `TALLY_AGENT_AUTO_UPDATE=off`), it downloads the installer the manifest names, checks it against the published SHA-256, and starts it detached with `--no-browser --server --config --install-dir` (`internal/autoupdate`). On a paired machine the installer runs its silent update: new binaries (each checked against the manifest), Windows service restarted, every company kept. Never on another OS, never a downgrade or a dev build, never while a sync is running, at most once an hour and three times per release (`autoupdate-state.json` next to `config.yaml`). Agents on v0.1.44 and earlier cannot update themselves; each machine needs one manual installer run to reach v0.1.45.

**v0.1.49 (unreleased) — the voucher header keys the invoice number (QA v27 L3).** A single-bill voucher was keyed by its party's bill-allocation reference ("New Ref" name) over the voucher header, so a mistyped or copied bill ref became the invoice number: FF Enterprises 2915 synced as 2982, 2930 as 2939 and 3146 as 3171 (each duplicating the real voucher of that number), Sampark SP/846/HR/26-27 as SP/849, GK Glass 62 and 63 both as 62, and a bill ref of "No" became an invoice number. `invoice_number` now comes from the header (`internal/tally/invoice_reference.go`): purchase side (purchases, RCM, debit notes) the supplier invoice number `REFERENCE`, then the voucher number; sales side (sales, credit notes) the company's own voucher number, then `REFERENCE`. The bill ref keys a row only when the header has neither, travels in the new optional row field `bill_reference`, and adds the normalization flag `reference_conflict` when it names a different number (compared without case, separators or leading zeros). Placeholder literals ("No", "NA", "N/A", "Nil", "None", "-", ".", "0", blank) never key a row: the next source is used, and `placeholder_reference` is flagged when only the narration hint or internal id was left. Within one sync run (one company and period), rows of different vouchers for the same party with the same normalised invoice number are all flagged `duplicate_number_in_period`. Consolidated (multi-bill) vouchers still key each split row by its bill name, never a placeholder one. Journals and payments are untouched (they carry bill refs as `against_invoice_refs`, not as an invoice key). Older servers ignore the new field and keep the flags as text.

**Unreleased — masters failures reach sync health (QA v21 G-A).** A failed or empty read of a company's Duties & Taxes masters, or of its ledger or group-tree masters, used to stay in the agent's local log while the run went on classifying without them. Every ingest batch of that run (invoice `/api/tally/ingest` and the journal, payment and tax-ledger lanes) now carries an optional top-level `sync_warnings` list: `code` (`duty_ledger_masters_unavailable`, `masters_fetch_failed` when Tally did not answer or refused the export, `masters_parse_failed` when its reply could not be read), `message` (the local log line, at most 500 characters), `tally_company`, `occurred_at` (RFC 3339, the time of the failed read, kept for lanes served from the 10-minute cache) and `affected_voucher_guids` (the live vouchers normalised without those masters, at most 500). At most 50 warnings per batch, de-duplicated by code, company and message; with healthy masters the field is omitted. The group-tree failure, which was silent, is now logged and sent too. Without the duty masters a GST-named leg stays `uncertain`, never GST or taxable value from its name (QA v27 L1 below). Older servers ignore the field.

**Unreleased — uncertain tax legs are quarantined, never dropped or guessed (QA v27 L1).** Companies whose duty-ledger graph was missing sent vouchers (KBS's "Debit Note - Material Rejection" notes among them) with GSTIN and taxable value but zero tax, which the server rejected. The agent now (1) reads the ledger and group-tree masters before the Duties & Taxes masters, fetches the group tree's `RESERVEDNAME`, and asks for duty ledgers under the company's own name for Duties & Taxes when it was renamed (`CHILDOF "Duties & Taxes"` found nothing there); (2) reads duty-ledger names from `NAME.LIST` / `LANGUAGENAME.LIST` and the parent from an attribute when Tally exports them that way; (3) when the duty masters still fail or come back empty, builds the graph from the ledgers the group tree places under Duties & Taxes (evidence `duty_group`, method `group`; GST head from the name, every row flagged), still sending `duty_ledger_masters_unavailable`; (4) with no graph, sends a plainly named tax ledger ("SGST INPUT") as role `uncertain`, method `name_fallback`, kept out of GST and taxable value, and flags the row with the machine-readable `normalization_flags` entry `tax_legs_uncertain` so GST Reco quarantines it visibly (reason `tax_legs_uncertain`); a name alone never creates a tax claim; (5) matches the party ledger line case- and space-insensitively, and names any invoice-family voucher it still cannot read into a row in a `vouchers_not_normalized` sync warning instead of dropping it silently. Debit notes take the same path as every invoice lane. Older servers ignore the new keys and values.

**Unreleased — each connection reports its own status (QA v29 L19).** One agent process serves several paired connections, but heartbeats carried one agent-wide `last_tick_status`, so one connection's 401 (`invalid_bearer`) or Tally failure was shown on every connection, naming another connection's company. Each connection now keeps its own last result and sends it as `connection_status` on its own heartbeat (`result`: `success` / `accepted_tick` / `rejected_auth` / `mapping_mismatch` / `endpoint_unreachable` / `wrong_company_open` / `idle`, plus `tally_endpoint` as host:port, `mapping_id`, `expected_company`, `open_companies`, `http_status`, `error_code`, a redacted `detail` of at most 300 chars, and `sync_request_id`, null until the server sends one). `last_tick_status` stays agent-wide for older servers. Before any master or voucher fetch, the mapped company's name and GUID must be what Tally has open on the port read: a same-name company with a different GUID on the mapped port is no longer read, and if the Tally probe cannot run nothing is read. Server error bodies are redacted (bearer, token-shaped values) before they reach a log line or a status. At startup the agent logs, for each connection, the keyring key names it read (never values).

**Unreleased — every run echoes the sync request it serves (QA v29 P3).** The server linked a run to an operator's "Sync now" request only by inferring from connection + period, so global runs could not count as proof for a request. When a heartbeat delivers `sync_now`, the agent now reads the optional response keys `sync_request_id`, `sync_request_period` (MMYYYY, or null for the current month; it wins over `pending_sync_period` when set) and `sync_request_kinds` (voucher kinds to walk; unknown names are logged and skipped, and an empty or all-unknown list walks every kind). The id travels by value from the poller (`heartbeat.SyncNow`) through the manual / current-month sync into `syncrun.WalkOptions.SyncRequestID` and `Request.SyncRequestID`, and is stamped as the optional top-level `sync_request_id` on every batch of every kind: invoice `/api/tally/ingest` (purchase, sales, credit and debit notes, the first batch that creates the run and the `is_final` one included) and the journal, payment and tax-ledger lanes. Masters pushes are not part of the run and carry no id. The id is part of the batch body, so a batch queued in the outbox keeps its original id on retry. A run serves exactly one request: sync_now actions are dispatched one at a time and each starts its own run with its own id; nothing holds an id between runs. Scheduled ticks and `agentctl` runs send no id. Older servers send none of the new keys (behaviour unchanged) and ignore the new batch key.

**Unreleased — company identity probe, observe by default (QA 04-Nov N1).** The gate's company check used Tally's built-in "List of Companies", which returns names only, so the same-name-different-GUID refusal never fired and mappings were stored without a GUID, while every export scopes by `SVCURRENTCOMPANY` name and Tally answers from whichever company is loaded. Every port now also gets an in-request TDL collection of Type `Company` fetching `NAME, GUID` (`tally.BuildCompanyIdentityXML` / `ParseCompanyIdentity`; a `LINEERROR`, `STATUS 0`, "Unknown Request" or missing collection is a failed probe, never "no company"). `agentctl identity-probe [--json]` runs both probes on every configured, mapped and listening port and prints, per port, each probe's companies (with GUIDs) and, per mapped company, whether each probe has it, its stored GUID and a verdict (`match`, `no_stored_guid`, `guid_mismatch`, `guid_not_returned`, `ambiguous`, `probes_disagree`, `identity_unavailable`, `not_open`, `unreachable`); read-only, no secrets. Autodiscover's catalog push now carries the GUID the Type:Company probe returns for a listed name (only when it returns exactly one), so mappings gain a GUID at setup/repair. The sync gate is unchanged by default (**observe**): `connection_status.detail` gains an `identity[observe]: …` clause and `open_companies` carries the probed GUIDs. Setting `company_identity_enforce: true` in `config.yaml` makes the GUID probe the gate (`syncrun.ResolveMappingEndpointsEnforced`): a company is read only where both probes list the same companies and the GUID probe returns the mapping's stored GUID; any doubt (probes disagree, GUID probe failed or returned no/several GUIDs, stored GUID not returned, same name with another GUID, or no stored GUID) blocks it before any Tally fetch with an `identity check (enforced): …` reason, never name-only trust. Turn it on per host only after `identity-probe` shows the probes agree there.

## Layout

```
cmd/
  agent/       long-running service entrypoint
  tray/        systray companion process
  agentctl/    CLI: `pair`, `status`
internal/
  version/     version string injected via -ldflags
  log/         zerolog + lumberjack rotation
```

The full target layout (ingest, pair, tally, scheduler, keyring, service, update) is documented in the master plan and filled in by later PRs.

## Build

```bash
make              # build all four binaries for the host platform → ./bin
make windows      # cross-compile for windows/amd64 → ./dist/windows-amd64
make release      # build all platforms → ./dist
go test ./...
go vet ./...
```

Go 1.24+ required. CI builds on `ubuntu-latest`.

`make windows` now produces `gstreco-tally-installer.exe` alongside
`gstreco-tally-agent.exe`, `gstreco-tally-agentctl.exe`, and the tray binary.
The release workflow also publishes raw Windows/Linux/macOS agent assets so
GST Reco's installer metadata endpoint can advertise direct download URLs
without forcing the app or installer to unpack zip bundles first.

## Signing

V1 ships **unsigned**. Users see a Windows SmartScreen warning on first run and walk through "More info → Run anyway". The server-side pair modal (GST Reco PR #98) renders the walkthrough. Code-signing options (Certum OSS, Microsoft Store MSIX, DigiCert EV) are parked in the master plan's "future purchase" section.
